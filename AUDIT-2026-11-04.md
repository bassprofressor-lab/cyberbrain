# Audit Cyberbrain 0.9.0 — 04.11.2026

Zweig `audit-2026-11-04` (Basis `2d1f823` = v0.9.0), Worktree `/root/cyberbrain-audit-1104`.
Nichts gepusht, nichts deployt, der Store `/root/orderflow/.cyberbrain` wurde nur gelesen.

## Ergebnis in einem Satz

Eine echte Lücke behoben: Über die Befehlszeile von `serve` (`POST /api/v1/command`) konnte jedes
lokale Programm, also auch ein Agent mit `curl`, als Betreiber in Ring 0 schreiben oder dort
löschen, obwohl `serve` genau das seit dem 29.09. verweigern soll. Offen bleibt die bekannte,
dokumentierte Schwäche der Agentenerkennung über `CLAUDECODE`. Dafür liegt ein konkreter Vorschlag
vor, der eine Entscheidung braucht.

## Befunde nach Schwere

### H1 — `serve /api/v1/command` umgeht die Ring-0/1-Sperre (Hoch, behoben `bc9453c`)

- **Wo:** `crates/cyberbrain/src/serve/command.rs` (`run`, Start des Kindprozesses) und
  `App::refuse_resident_writes` (`app.rs`).
- **Was:** `serve` öffnet den Store als Betreiber und setzt `refuse_resident_writes()`, solange es
  nicht mit `--allow-resident-writes` gestartet wurde. `POST /notes` wird dadurch abgewiesen.
  `POST /command` startet aber einen frischen `cyberbrain`-Prozess. Der ist Betreiber und weiß von
  der Sperre nichts. `write --ring 0 …`, `forget <ring-0-notiz>` und `review --accept` eines
  Ring-0-Vorschlags gingen durch, und die Auditzeile nannte `operator`. Eine so geschriebene Notiz
  gilt als bestätigt und wird damit in jede Sitzung und jeden Unteragenten eingespielt.
- **Wen es trifft:** Die Desktop-App startet `serve --terminal` immer, ohne
  `--allow-resident-writes`. Auf S1 läuft kein `serve`, nur `mcp --http`, und das arbeitet als Agent.
- **Behebung:** Der Kindprozess bekommt `CYBERBRAIN_REFUSE_RESIDENT_WRITES=1`, `App::open` hält sich
  daran, dazu `CYBERBRAIN_NO_DAEMON=1`, denn der Daemon öffnet ein eigenes `App`, das von der Sperre
  nichts weiß. Die Variable kann nur einschränken.
- **Beleg:** `tests/cli.rs::a_process_started_for_a_served_store_inherits_its_resident_refusal`
  (als Betreiber) war auf dem alten Code ROT (Ring-0-Schreiben Exit 0, Datei in `notes/r0`) und ist
  jetzt GRÜN. Dazu `serve::tests::a_served_store_does_not_write_rings_zero_and_one_through_the_command_line`
  für die Route. ⚠️ Startet man den Serve-Test aus einer Claude-Code-Sitzung, ist er auch auf dem
  alten Code grün, weil das Kind dann über `CLAUDECODE` als Agent gilt. Deshalb ist der CLI-Test der
  Beweis. Diese Falle hat die Lücke vermutlich bisher verdeckt, siehe Vorschlag F5.

### M1 — Die Agentenerkennung ist mit vier einfachen Schreibweisen zu umgehen (Mittel, offen, Entscheidung)

- **Wo:** `hook/events.rs::bash_verdict_on` (Textprüfung vor jedem Bash-Aufruf), `main.rs::cli_actor`,
  `daemon.rs::peer_agent`.
- **Nachgestellt** (Unit-Probe gegen `bash_verdict`, alle vier wurden durchgelassen):
  1. `env -i bash -c 'cyber''brain write --ring 0 …'`
  2. `X=cyberbrain; env -i $X write --ring 0 …`
  3. `python3 -c "import os; os.environ.pop('CLAUDECODE'); os.system('cyberbrain write --ring 0 …')"`
  4. `env -i /usr/local/bin/cyber\brain write --ring 0 …`

  Jede dieser Zeilen schreibt Ring 0 als Betreiber, bestätigt und eingespielt. Beim Daemon reicht
  ein Client, der unter `env -i` gestartet wird, denn `peer_agent` liest nur die Umgebung des
  direkten Gegenübers.
- **Einordnung:** Das ist dokumentiert (`site/src/pages/concepts.md`, „not a boundary against an
  agent that sets out to lie“). Ein ehrlicher Agent tut das nicht. Ein durch Prompt-Injection
  gekaperter Agent kann es aber, und Ring 0 bindet danach jede weitere Sitzung.
- **Vorschlag, nicht eingebaut:** Unter Linux zusätzlich die Ahnenkette prüfen, also
  `/proc/<ppid>/environ` bis PID 1 mit `ppid` aus `/proc/<pid>/stat`. `/proc/<pid>/environ` steht ab
  dem `exec` fest. Die Bash, die Claude Code startet, trägt `CLAUDECODE=1`, gleich was ihre Kinder
  danach abstreifen. Dasselbe für den Daemon ab dem Peer-PID. Das sind wenige Lesezugriffe je
  CLI-Aufruf und kostet keine Kontext-Tokens. Es fängt alle vier Schreibweisen. Es fängt keinen
  Doppel-Fork, der den Prozess an PID 1 hängt (`setsid -f`), und die Textprüfung bleibt davor stehen.
  **Nicht selbst eingebaut, weil es das Vertrauensmodell ändert:** `tests/cli.rs`
  (`env_remove("CLAUDECODE")`) und `ui/e2e/serve.ts` (`delete e.CLAUDECODE`) laufen aus einer
  Claude-Sitzung heraus heute als Betreiber und wären dann Agent. Sie bräuchten einen Schalter, der
  nur in Debug-Builds wirkt.

### N1 — Übergabe mit Datum in der Zukunft gilt als neueste und als frisch (Niedrig, behoben `5a1d952`)

- **Wo:** `hook/handoff.rs::latest`/`age_words`.
- **Was:** `updated` in der Zukunft (Handbearbeitung, eine vorgehende Uhr, eine Notiz von einem
  anderen Rechner) blieb die angezeigte Übergabe, bis das Datum erreicht war, angezeigt als
  „0 min ago“.
- **Behebung:** Richtig datierte Notizen gehen vor. Eine allein angezeigte sagt „dated in the
  future“. 5 Minuten Uhrenabweichung werden geduldet. Bei richtigem Datum bleibt der Startkontext
  gleich, es entstehen also keine Mehrkosten.
- **Beleg:** `hook::tests::a_handoff_dated_in_the_future_does_not_pass_for_fresh`, vorher ROT,
  jetzt GRÜN.

### N2 — Governance sieht MCP-Werkzeuge nicht (Niedrig, offen)

`hook/governance.rs::TOOLS` ist fest auf Bash, Edit, Write, MultiEdit, NotebookEdit und WebFetch
gesetzt. Aufrufe von `mcp__*`-Werkzeugen (etwa ein Dateisystem- oder Datenbank-MCP) und WebSearch
erreichen AgentGuard auch im Modus `enforce` nicht. Vorschlag F3.

### Hinweise ohne Handlungsdruck

- `worktree.rs::locate`: Ein `.git`, das selbst ein Symlink ist, wird übersprungen. Eine
  `.git`-Datei ohne lesbares `commondir` beendet die Suche, statt weiter oben zu suchen. Beides
  führt zum alten Verhalten, nicht zu einem falschen Store.
- `cargo test --workspace` mit Standard-Features scheitert in einem frischen Checkout an
  `serve::tests::csp_is_a_header…` (404, weil `ui/dist` fehlt). Die CI testet mit
  `--no-default-features`, deshalb merkt man es dort nicht. Für Entwickler ist es eine Falle.
- `cyberbrain-embed/src/weights.rs`: `rows * dim * 4` ist ungeprüft. Das ist heute sicher, weil
  `safetensors` die Größen mit `checked_mul` prüft und das Modell über einen Hash geprüft wird. Ein
  `checked_mul` würde die SAFETY-Begründung unabhängig von der Fremdbibliothek machen.
- `SECURITY.md` nannte noch „v0.7.6“. Korrigiert.

### Geprüft, ohne Befund

Host-/Origin-Wächter von `serve` (DNS-Rebinding, CSRF), Peer-UID-Prüfung über `/proc/net/tcp`.
`mcp --http`: Token mit konstanter Laufzeit verglichen, Bindung nur an private Adressen, `Origin`
wird abgewiesen. TLS-Pin: Das Zertifikat wird verglichen, die Signaturen prüft weiter der Provider.
`find` folgt keinen Symlinks und lässt den Store aus. Store-Suche mit Eigentümerprüfung, auch über
den Worktree-Rückfall. Atomare Schreibvorgänge mit Store-Sperre. `unsafe`-Blöcke (libc, mmap) haben
alle eine Sicherheitsbegründung. Zufallseingaben in die Parser: keine Panik (siehe Tests).
